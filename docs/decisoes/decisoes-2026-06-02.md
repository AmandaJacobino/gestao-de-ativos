# Decisões — Sessão 2026-06-02

> Sessão de levantamento dos Fluxos 1 e 2
> Participantes: Amanda
> Formato: Revisão do documento de projeto + respostas às lacunas identificadas

---

## D-01 — Aurora, Sentinel e FlowTrack são sistemas, não dispositivos

**Decisão:** Os três produtos da empresa são sistemas de monitoramento. Cada sistema trabalha com um tipo específico de dispositivo:
- **Aurora** → dispositivo **Prism**
- **Sentinel** → dispositivo **Nexus**
- **FlowTrack** → kit composto por múltiplos itens (ver D-02)

**Por que importa:** Os nomes dos sistemas são os usados no SalesGrid e nos contratos. O sistema de gestão deve mapear corretamente entre o nome do sistema e o tipo de dispositivo físico.

---

## D-02 — Composição do kit FlowTrack

**Decisão:** Um contrato FlowTrack inclui o seguinte kit por unidade contratada:
- 1× DataHub (dispositivo principal)
- 3× Hastes
- 1× Celular
- 1× Fone
- 2× Carregadores (um para o celular, um para o coletor)
- 2× Cabos (um para o carregador do celular, um para o coletor)

**Aberto:** Ainda não foi decidido se o sistema de gestão rastreará somente o DataHub (ativo principal) ou todos os itens do kit como ativos individuais (ver lacuna L-05 atualizada).

**Resposta:** O sistema deve rastrear cada item do kit, cada item tem um número de série em sua etiqueta, eles devem ser cadastrados no sistema também. Cada dispositivo FlowTrack deve informar quais itens o estão acompanhando em kit quando for enviado para o cliente. 

---

## D-03 — Dispositivo Fusion em desenvolvimento

**Decisão:** Existe um quarto dispositivo em desenvolvimento: o **Fusion** (combina Prism e Nexus). Já está em uso em Portugal. Deve ser previsto nos campos de tipo do sistema.

---

## D-04 — NF de Compra é campo obrigatório no cadastro

**Decisão:** Sem `Número da NF de Compra` e `Data de Emissão`, o cadastro de dispositivos não pode ser concluído. O sistema bloqueia.

---

## D-05 — Serial é chave primária e deve ser único

**Decisão:** O sistema deve impedir, em tempo real, o cadastro de dois dispositivos com o mesmo número de serial. Em caso de duplicata em importação de lote, a linha é rejeitada com indicação do motivo; as demais são importadas normalmente.

**Atualização (2026-06-03):** Após o processamento da planilha, o sistema deve exibir uma **pré-visualização** dos resultados, **destacando as linhas com serial duplicado** para facilitar a correção por Operações antes de confirmar a importação.

---

## D-06 — Cadastro em lote: .xlsx e .csv com modelo padrão

**Decisão:** O sistema deve disponibilizar um modelo padrão de planilha (formatos .xlsx e .csv) para download direto na tela de importação em lote. O upload aceita apenas esses dois formatos **no modelo padrão**.

---

## D-07 — Integração Omie para NF de Saída

**Decisão:** A integração com Omie deve puxar automaticamente o número da NF de saída após a emissão. Caso a API não retorne o número, o campo pode ser preenchido manualmente como fallback.

**Documentação da API Omie:** fornecida por Amanda durante a sessão (URL registrada internamente pelo dev).

**Atualização (2026-06-03) — T-01 validada:** A integração é **viável**. APIs do Omie identificadas:
- **NF-e → Consultas** — lista as NF-e emitidas; permite capturar o número da nota automaticamente após a emissão. `https://app.omie.com.br/api/v1/produtos/nfconsultar/`
- **Utilitários de NF-e** — recupera a URL do XML, do DANFE (PDF) e o logo; útil para guardar o arquivo junto ao registro do ativo. `https://app.omie.com.br/api/v1/produtos/notafiscalutil/`
- **Pedidos de Venda** — o sistema cria o pedido via API → o pedido aparece no Omie para o Fiscal faturar e emitir a NF. `https://app.omie.com.br/api/v1/produtos/pedido/`
- **Faturamento de Pedido** — executa o faturamento do pedido; permitiria disparar a emissão automaticamente, sem ação manual do Fiscal. `https://app.omie.com.br/api/v1/produtos/pedidovendafat/`

**Nova pendência (T-04):** Decidir se o sistema apenas **cria o Pedido de Venda e consulta a NF** após o Fiscal emitir, ou se **dispara o faturamento automaticamente** via API — decisão de escopo e de permissão.

**Atualização (2026-06-15)** - Após uma reunião com o setor fiscal foi decidido não integrar mais o Omie, todo o processo de cadastro do número da nota fiscal será feito manualmente pelo time de operações. 

---

## D-08 — Sem prazo máximo para emissão da NF de Saída

**Decisão:** O sistema apenas bloqueia a liberação física do dispositivo enquanto a NF não estiver registrada. Não há contagem de prazo, alerta de atraso ou SLA — o bloqueio é indefinido até a NF ser preenchida.

---

## D-09 — API dos Correios: polling (não webhook)

**Decisão:** A API dos Correios (SRO/SIGEP) não oferece webhooks — funciona somente via polling. O sistema consultará periodicamente o status de rastreamento.

**Intervalo de polling:** a ser definido pelo dev. Sugestão: a cada 4 horas para não sobrecarregar a API.

**Notificados em cada mudança de status:** cliente e Operações.

**Atualização (2026-06-03) — T-02 definida:** O polling deve ocorrer **no máximo duas vezes ao dia**, em horários estratégicos. É suficiente para acompanhar o envio sem sobrecarregar a API.

---

## D-10 — Comportamento ao entregar por tipo de dispositivo

**Decisão:**
- **FlowTrack:** não requer instalação. Status muda para 🟢 **Em Operação** automaticamente ao ser confirmada a entrega pelos Correios.
- **Prism, Nexus e Fusion:** requerem instalação física. Status fica em ⚪ **Entregue** até o dispositivo ser instalado e estar comunicando, quando então muda para 🟢 **Em Operação**.

**Aberto:** Como o sistema detecta que o Prism/Nexus/Fusion está comunicando? Ação manual ou integração com plataforma IoT? (ver lacuna L-08)

**Resposta:** O sistema fará integração com APIs internas dos nossos sistemas, e através dela será informada a comunicação dos dispositivos. 

---

## D-11 — Falha na entrega: notificação e tratativa manual

**Decisão:** Em caso de falha na entrega (endereço errado, recusa, extravio), o sistema notifica cliente e Operações. A tratativa é manual entre as partes. Não há fluxo automatizado para reenvio.

---

## D-12 — Campo de tipo/quantidade no SalesGrid já existe

**Decisão:** O campo que registra tipo e quantidade de dispositivos em um contrato já existe no SalesGrid. Não é necessário criar — apenas mapear na integração.

---

## D-13 — Aprovação parcial de reserva

**Decisão:** Quando o estoque for menor que a quantidade solicitada, o sistema deve exibir para Operações:
- Quantidade disponível em estoque
- Quantidade em manutenção (indisponível)
- Prazo previsto de retorno da manutenção

Operações seleciona o que há disponível e preenche o campo **OBS** com o que faltou e quando será enviado. A solicitação é marcada como parcialmente atendida.

---

## D-29 — Complemento de solicitação parcial é manual e em massa (L-04)

**Decisão:** Quando os dispositivos que faltaram em uma aprovação parcial chegam ao estoque, o complemento da solicitação é **manual**. O sistema deve permitir que Operações **selecione os dispositivos em massa** para concluir a solicitação pendente.

**Exemplo:** Faltaram 20 dispositivos para uma solicitação. Quando chegam ao estoque, Operações seleciona os 20 de uma vez (em massa) e completa o atendimento. Fecha **L-04**.

---

## D-30 — Canal de notificação ao cliente (P-03)

**Decisão:** O cliente acompanha o rastreamento pelo **sistema**, caso tenha acesso. Caso não tenha acesso, as notificações de rastreamento são enviadas por **e-mail e/ou WhatsApp**. Fecha **P-03**.

**Nova pendência (T-05):** Definir os serviços de integração para os canais de notificação — provedor de **e-mail transacional** e **WhatsApp** (ex: WhatsApp Business API) — a ser especificado pelo dev.
